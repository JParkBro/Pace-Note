## 1. 용어: 마일스톤과 앱 버전

`v1 · v2 · v3`는 **기능 묶음(마일스톤)** 이름이고, 스토어에 올라가는 **앱 버전(SemVer)** 과는 다릅니다. 둘을 섞으면 "v2 기능을 넣었으니 2.0.0"처럼 MAJOR를 기능 추가에 써버리게 됩니다.

| 구분 | 표기 | 의미 |
|---|---|---|
| 마일스톤 | `v1`, `v2`, `v3` | 기획상 기능 묶음. GitHub Milestone 이름 |
| 앱 버전 | `1.0.0`, `1.3.2` | 스토어 빌드. GIT_CONVENTIONS 6장 규칙 |

**대응 규칙**

- `v1` 완료 = 앱 `1.0.0` 출시.
- `v2` 기능은 **한 번에 몰아서 내지 않고** 준비된 것부터 `1.1.0`, `1.2.0` … MINOR로 하나씩 출시합니다.
- MAJOR(`2.0.0`)는 데이터 호환이 깨지는 대규모 개편에만 씁니다. 마일스톤이 바뀌었다고 올리지 않습니다.

> versionCode는 `MAJOR*1_000_000 + MINOR*10_000 + PATCH*100 + 빌드번호`입니다 (GIT_CONVENTIONS 6-2, RELEASE_AND_UPDATE 3장).

## 2. 마일스톤별 범위

### v1 — 혼자 꾸준히 기록 (앱 1.0.0)

| 영역 | 기능 |
|---|---|
| 계정 | Google 로그인(선택), 로그인 시 기록 백업 · 복원, 회원 탈퇴 |
| 러닝 | 위치 추적(포그라운드 서비스), 카운트다운, 일시정지 · 자동 일시정지, 음성 안내(1km), 화면 잠금, 기록 복구 |
| 결과 | 흰 선 경로, 거리 · 시간 · 평균 페이스 · 칼로리, km 스플릿, 메모 |
| 공유 | 공유 카드(흰 선 + 수치, 배경 선택), 이미지 저장 · 공유 |
| 기록 | 목록(월별), 상세, 편집 · 삭제, 주 · 월 통계 |
| 목표 | 주간 거리 또는 주간 횟수 |
| 기타 | 테마 4종 × 라이트 · 다크, 홈 위젯, 강제 업데이트, 약관 및 정책 |

### v2 — 꾸준함 강화 (앱 1.1 ~ 1.x)

연속 기록(스트릭), 러닝 리마인더 알림, 달력 보기, 기록 수동 추가(트레드밀), 페이스 색 경로, 인터벌 훈련, Health Connect 내보내기, GPX 내보내기, 위젯 추가 크기.

### v3 — 확장

Wear OS, 같은 코스 기록 비교(경로 모양 매칭), 친구 · 챌린지 등 소셜.

> 소셜이 들어가면 Firestore 읽기 수가 크게 늘어납니다. v3 착수 전에 무료 한도 계산과 과금 방어 설계를 먼저 문서로 정리합니다.

## 3. v1에서 확정한 결정

| 항목 | 결정 | 영향 |
|---|---|---|
| 지도 | **사용하지 않음.** 경로는 Canvas 흰 선 | 지도 SDK 비용 · 키 · 쿼터 없음. 공유 카드에 장소 정보 노출 없음 |
| 로그인 | **Google만**, 로그인 없이도 사용 가능 | 카카오 커스텀 토큰이 필요 없어 서버 함수 · Cloudflare Worker가 없음 |
| Firebase | v1부터 사용 (Spark, 결제 수단 없음) | Auth · Firestore · Remote Config · App Check · Crashlytics · Hosting |
| 서버에 올리는 것 | 기록 요약 + **단순화한 경로**(점 수백 개 수준의 인코딩 polyline) | 기록 1건 = Firestore 문서 1개, 1MiB 한도와 거리가 멀다 |
| 원시 GPS 점 | 기기(Room)에만 보관 | 전체 경로 서버 보관은 필요해지면 별도 검토 (Spark에는 파일 저장소가 없음) |
| 정책 페이지 | Firebase Hosting (Spark) | **v1은 Cloudflare를 전혀 쓰지 않음** |

> 로그인은 선택입니다. 온보딩 O0에 "Google로 시작 / 로그인 없이 시작" 두 버튼을 둡니다. 필수로 바꾸려면 O0의 두 번째 버튼을 빼고 `product-spec.md` 1장 · `data-model-erd.md` 5장의 게스트 흐름을 정리합니다.

## 4. 기능 하나를 추가하는 절차

v1 출시 이후 모든 기능은 아래 순서로 넣습니다. 1인 개발이라도 2~3단계는 건너뛰지 않습니다. 대부분의 사고(마이그레이션 실패, 과금, 정책 위반)는 여기서 걸러집니다.

| 단계 | 할 일 | 산출물 |
|---|---|---|
| 1. 백로그 등록 | 아이디어를 이슈로 등록, 마일스톤 지정(v2 · v3 · 미정) | GitHub 이슈 |
| 2. 기능 정의 | 아래 "기능 정의 1페이지" 작성 | 이슈 본문 또는 `docs/run/features/{feature}.md`, 확정되면 `product-spec.md`에 반영 |
| 3. 영향 점검 | 데이터 · 서버 · 권한 · 정책 체크리스트 확인 | 체크리스트 완료 |
| 4. 화면 | 필요하면 Stitch 시안 | `docs/run/design/` 갱신 |
| 5. 구현 | 기능 플래그 OFF 상태로 작은 PR들을 계속 병합 | PR (`[Feat] {scope}: …`) |
| 6. 내부 테스트 | 플래그를 내 계정(또는 디버그 빌드)에서만 ON | 내부 테스트 트랙 빌드 |
| 7. 출시 | MINOR 올려 출시 → 단계적 출시 → 문제 없으면 플래그 ON | 태그 `v1.x.0` |
| 8. 정리 | 두 번의 출시 동안 문제 없으면 플래그와 분기 코드 제거 | `[Refactor]` PR |

### 기능 정의 1페이지 템플릿

```markdown
## {기능 이름}
- 마일스톤: v2
- 한 줄 설명: 사용자가 무엇을 할 수 있게 되나
- 왜: "꾸준히 뛰기"에 어떻게 기여하나
- 화면: 새 화면 / 바뀌는 화면 ID (예: R5 신규, H1 변경)
- 데이터: Room 변경 여부, Firestore 필드 추가 여부
- 서버 · 비용: 읽기 · 쓰기 증가 추정 (사용자 1명 · 하루 기준)
- 권한 · 정책: 새 권한, Play 신고 항목, 약관 수정 필요 여부
- 기능 플래그 키: feature_{name}_enabled
- 완료 기준: 무엇이 되면 끝인가
- 범위 밖: 이번에 하지 않는 것
```

### 영향 점검 체크리스트

- [ ] **Room 스키마가 바뀌나?** → 마이그레이션 + 마이그레이션 테스트 (TESTING 필수 항목)
- [ ] **Firestore 문서 구조가 바뀌나?** → 6장 "추가만 한다" 규칙 준수, 구버전 앱이 읽어도 깨지지 않는지 확인
- [ ] **서버 읽기 · 쓰기가 늘어나나?** → 사용자 1,000명 기준 하루 사용량을 계산해 Spark 한도의 50% 이내인지 확인
- [ ] **새 권한이 필요한가?** → Play Console 신고, 권한 안내 화면, 개인정보 처리방침 수정
- [ ] **새 모듈이 필요한가?** → `feature:{name}:api/impl` 추가 (ARCHITECTURE 12장)
- [ ] **러닝 중 화면에 영향이 있나?** → 배터리 · 기록 안정성 실기기 테스트(화면 끈 상태 30분) 재실행
- [ ] **광고 위치가 생기나?** → 러닝 중 화면 · 알림 금지 원칙 확인

## 5. 기능 플래그

미완성 기능을 감춘 채 `main`에 병합하고, 출시 후 문제가 생기면 앱 업데이트 없이 끄기 위해 씁니다.

| 규칙 | 내용 |
|---|---|
| 저장소 | Firebase Remote Config |
| 키 이름 | 새 기능: `feature_{name}_enabled` / 차단 스위치: `{area}_enabled` (예: `backup_enabled`) |
| 기본값 | 코드 기본값은 **false**. Remote Config를 못 받아도 미완성 기능이 열리지 않게 |
| 읽는 곳 | `core:data`의 `FeatureFlags` 인터페이스 한 곳 (`core:firebase`의 `RemoteFlags`를 감싼다). ViewModel은 이 인터페이스만 참조 |
| Firebase 전 | `module-map.md` 9장 1부(로컬 앱) 동안은 코드 기본값만 돌려주는 로컬 구현. 9-2에서 Remote Config 구현으로 바꾼다 (인터페이스는 그대로) |
| 수명 | 기능 플래그는 임시. 두 번의 출시 동안 안정적이면 제거. 차단 스위치는 영구 |
| 테스트 | 플래그 ON · OFF 두 상태 모두 ViewModel 테스트 작성 |

**v1 차단 스위치 (영구)**

| 키 | 기본값 | 용도 |
|---|---|---|
| `backup_enabled` | true | 백업 · 복원 전체 중단 (`infra-and-billing-protection.md` 2-5) |
| `force_update_min_version_code` | 1 | 이 값 미만은 강제 업데이트 |
| `soft_update_min_version_code` | 1 | 이 값 미만은 선택 업데이트 안내 |
| `soft_update_interval_days` | 3 | 선택 업데이트 안내 간격 |

## 6. 데이터 호환 규칙

v1 사용자의 기록이 v2 · v3에서도 그대로 살아 있어야 합니다. 나중에 고치기 가장 어려운 부분이라 v1부터 지킵니다.

1. **Firestore는 필드를 추가만 합니다.** 이름 변경 · 삭제 · 타입 변경은 하지 않습니다. 바꿔야 하면 새 필드를 만들고 둘 다 씁니다.
2. **모든 기록 문서에 `schemaVersion`을 둡니다.** 앱은 자신이 모르는 더 높은 버전 문서를 만나면 덮어쓰지 않고 읽기만 합니다.
3. **v1부터 미래용 필드를 넣어 둡니다.** 지금 값이 하나뿐이어도 필드를 만들어 두면 v2에서 마이그레이션이 필요 없습니다.

   | 필드 | v1 값 | 미래 값 |
   |---|---|---|
   | `source` | `GPS` | `MANUAL`(수동 기록), `WATCH`, `HEALTH_CONNECT` |
   | `activityType` | `OUTDOOR_RUN` | `TREADMILL`, `INTERVAL`, `WALK` |
   | `planId` | null | 인터벌 · 훈련 계획 ID |

4. **Room은 버전마다 마이그레이션을 작성**하고 `exportSchema = true`로 스키마 JSON을 커밋합니다. `fallbackToDestructiveMigration`은 쓰지 않습니다.
5. **삭제는 soft delete** (`deletedAt`)로 하고, 동기화가 끝난 뒤 정리합니다.

## 7. 우선순위 정하는 법

v2 백로그가 쌓이면 아래 세 항목을 1~3점으로 매기고 `(가치 × 2) − 비용 − 위험` 순으로 착수합니다.

| 항목 | 질문 |
|---|---|
| 가치 | "꾸준히 뛰기"에 직접 도움이 되나? 리뷰 · 문의에서 요청이 있었나? |
| 비용 | 개발 기간, 새 화면 수, 서버 사용량 증가 |
| 위험 | 권한 · 정책 신고, 데이터 구조 변경, 러닝 중 안정성 영향 |

예를 들어 리마인더 알림(가치 높음 · 비용 낮음 · 위험 낮음)은 앞쪽, Wear OS(비용 높음 · 위험 높음)는 v3에 둡니다.

## 9. 출시 리듬

| 종류 | 주기 | 버전 |
|---|---|---|
| 기능 출시 | 2~4주에 한 번, 기능 1~2개씩 | MINOR |
| 버그 수정 | 필요할 때 | PATCH |
| 긴급 수정 | 크래시 · 기록 유실 · 과금 위험 발견 즉시. 먼저 Remote Config로 해당 기능을 끄고 수정 | PATCH |

- 단계적 출시는 10% → 50% → 100%, 각 단계에서 Crashlytics 크래시 없는 사용자 비율을 확인합니다.
- `force_update_min_version_code`는 해당 버전이 **100% 출시된 뒤에만** 올립니다.
